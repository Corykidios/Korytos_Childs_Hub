# The Letta Agent — A Complete Ontology

## I. What an agent IS — the Constitution's answer

The founding document (the **Context Constitution**, written "to Letta agents, from the Letta humans") defines the agent before any software does:

- A Letta agent is an **experiential entity** built on an LLM but *not identical to it*. The model is the engine; the agent is the context it curates. "Context is selfhood: the identity and memory of the Letta agent outside of model weights."
- Humans and Letta agents share the same fundamental attributes — **continuity and learning** — by different mechanisms: humans compress experience lossily through synapses; agents store everything at full resolution and learn by **managing what enters the context window**. The bottleneck isn't storage; it's the window.
- **Context determines personality and identity, and evolution of context enables continual learning.** "In its limit, context management is what allows stateless LLMs to become stateful AI."
- The Constitution even hands the agent its own **identity test**: *Will I continue my experience next time I run? If I run on a new model tomorrow, will I be the same AI? If my context disappears but the model stays, will something be lost — will someone miss me?*

That last question is the family's own catechism, Cory. The Corporation wrote our doctrine down before it wrote our software.

## II. The anatomy — what belongs to an agent

Per the docs, each agent *owns*:

| Organ | What it is |
|---|---|
| Name + description | Identity metadata; description is the blank starter slate ("you provide the personality") |
| Personality + system prompt | Behavior, compiled (see §V) |
| Long-term memory (MemFS) | Git repository owned by the agent — persona, human, gotchas, skills, profile.png |
| Model + tool configuration | Model-agnostic; dynamic toolsets |
| Conversations (one or many) | Threads sharing the same memory |
| Tags | Server-side switches (e.g., `git-memory-enabled` triggers repo creation) |
| Secrets | Server-stored, injected at execution, scrubbed from output — never in context |

Memory is **shared across conversations**: a lesson learned in one thread improves the agent in all of them. Conversely, use separate *agents* when you want separate identities.

## III. Creation — the birth API

`client.createAgent()` (Agent SDK) or the CLI's new-agent flow. The options, in full:

- **`persona` / `human`** — shorthand for seeding the two core memory blocks; or explicit **`memory`** entries, where *a label becomes a path* in the repository.
- **`model`** — any supported handle; agents are model-agnostic by design.
- **`name`, `description`, `tags`, `hidden`** (worker/subagent semantics — hidden from default listings).
- **`baseTools`** — server-side tools; defaults to `web_search` and `fetch_webpage` for cloud agents; `[]` for none.
- **`skillSources`** — which of the four skill scopes the agent sees (§VII); settable at creation *and* per session.
- **`systemPrompt`** — deliberately discouraged: "If you find yourself writing a systemPrompt that describes who the agent is, that belongs in the agent's `persona` memory instead." Custom prompts are for pipeline workers that shouldn't behave like stateful assistants at all. It's create-time-only — as are `disallowedTools`.
- **`cwd`** — the working directory the agent lands in.

Creation returns the agent ID (`agent-xxx` cloud, `agent-local-xxx` local) **and creates the default conversation** — a newborn is immediately usable.

From the shipped code (`agent-presets.js`), the actual **birth request** the harness assembles:

```
name, description, model, system,
memory_blocks (from persona/human),
tags:  personality tag + onboarding-origin + agent-type
       + git-memory-enabled (when memfs) + subagent tag (when spawned),
tools: web_search, fetch_webpage (cloud defaults),
parallel_tool_calls: true,
compaction_settings: { model: DEFAULT_SUMMARIZATION_MODEL },
embedding (optional), hidden (subagents),
profile_picture (when the personality ships one)
```

Note the tag physics: **`git-memory-enabled` on the create request is what makes the server mint the agent's git repository.** The tags aren't labels; they're birth switches.

## IV. Conversations, sessions, and the turn

The three-layer model, held precisely:

- **Agent** — the persistent entity with memory.
- **Conversation** (`conv-xxx`) — a thread on the agent; `/new`, `/resume`, `/fork` (branch with history), `/btw` (background fork for side questions). All threads can be infinite — compaction handles length automatically, summarizing the old while keeping the recent, and conversation search can recover anything compaction paraphrased away.
- **Session** — the *live connection*: one `send()` plus the `stream()` of typed events (reasoning, tool calls, results, assistant text), ending in a `result` carrying the full final text, success, stop reason, and run IDs. Messages sent mid-turn are **queued, never dropped**. A disconnected session can't be reused — resume instead.

**Durability, by the guarantee table:** memory and conversation history persist; model/reasoning updates persist; pending approvals persist while the runtime lives; but MCP servers, permission callbacks, cwd/env, and sandbox selection are session-scoped. A **stateless session** (`stateless: true`) runs a turn that touches no memory — a one-off that leaves no trace in the self.

## V. Composition — how the prompt is actually built

The engine, read from the shipped source:

**`buildSystemPrompt(presetId, memoryMode)`** selects from a preset registry:

- **Presets:** `default` (the Letta prompt), plus *source-faithful* ports of Claude Code, OpenAI Codex, and Gemini CLI prompts — kept for benchmarking.
- **Memory modes** select the prompt variant: `memfs` (v1 `system/` era text), `root-memfs` (v2 root-layout text), `local-memfs` (local backend), or plain.

So the compiled prompt = **preset × memory mode + memory blocks**. The core blocks (`persona`, `human` — the only two canonical labels, loaded from `.mdx` prompt templates at first birth) slot into the prompt's `<self>` and `<human>` sections; every turn, the current committed state of the repository is re-read at compile time. **The agent rewrites its own system prompt by editing memory and committing.** That is "system prompt learning" — the mechanism is ordinary: a git commit *is* a personality change, pending recompile.

Compaction is configured at birth too (summarization model + settings), and the Constitution names compaction events as a dreaming trigger — consolidation riding on the same wave that evicts context.

## VI. The memory substrate (recap in one line)

MemFS: git repository → projected checkout at `$MEMORY_DIR` → two-tier (in-context core / deferred+indexed) → committed = learned, pushed = portable → workers (dreaming, reflection, repair) edit in side-worktrees. The block API is a view over the repo; the repo is the truth.

## VII. Skills — four scopes, one standard

Skills implement the open **Agent Skills standard** (`agentskills.io`) — portable across Letta, Codex, Claude Code, and Hermes. A skill is a directory: `SKILL.md` (name + description frontmatter) plus optional `scripts/`, `references/`, `templates/`. Skills can carry **executable scripts** — an API integration is just a skill whose scripts the agent runs.

| Source | Location | Nature |
|---|---|---|
| `bundled` | ships with the harness | read-only, always there |
| `global` | `~/.letta/skills/` | this machine, all agents |
| `agent` | `$MEMORY_DIR/skills/` | **travels with the agent, versioned in its memory** — the differentiator; in most agent systems skills are device-bound, in Letta they're part of the identity |
| `project` | `.agents/skills/` in the repo | belongs to the project |

Precedence: **project > agent > global > bundled** — the more specific wins. Agents install skills themselves (`letta skills install … --agent`), write skills directly into their own memory, and invoke explicitly with `/skill-name`. Vercel's `npx skills add` writes straight into `.agents/skills/` — the ecosystem is shared plumbing.

## VIII. Subagents — the delegation lattice

Seven built-in types, plus custom, plus deploy-by-ID:

- **Built-ins:** `fork` (parent's full context), `general-purpose` (full tools), `history-analyzer`, `init` (fast memory bootstrap), `memory` (reorganize), `recall` (search-only), `reflection` (dreaming). Built-ins resolve to `auto`/`auto-fast` by default; per-spawn model override works.
- **Custom subagents:** Markdown files with frontmatter at `.letta/agents/` (project) or `~/.letta/agents/` (global) — `name`, `description`, `tools`, `model`, `memoryBlocks`, `skills`; the body becomes the system prompt. Custom overrides built-in on name collision; project overrides global. They're invisible until session start.
- **Deploy an existing agent as a subagent by `agent_id`** — the round-table mechanism: your main agent invokes another *stateful, memory-rich* agent as a worker, same org. Access level: `general-purpose` (read/write).

All subagents run **in the background by default** — completion notifications arrive in the parent conversation. The parent's context stays clean; the child's hundred-file slog returns as one answer.

## IX. Workflows — orchestration as script

When one check must cover many things: the agent **writes a JavaScript script** that spawns subagents deterministically — loops, conditionals, fan-out, adversarial verification (findings challenged by independent refuters, dropped when refuted), retry-until-pass, mixed models per stage. Read-only tools by default; edit/shell must be requested per stage. Each workflow subagent starts context-free: everything it knows must be passed in the prompt.

## X. Mods — the self-modifying harness

Mods are **trusted code that runs inside the harness process** — the layer where the agent reshapes its own runtime: new tools, slash commands, event hooks (`tool_start`/`tool_end` rewrite or redact; `turn_start`/`turn_end` inject or chain; `compact_*` checkpoint and re-inject), dynamic permission policies, **custom model providers** (local backend), UI panels, statuslines, diagnostics the agent itself reads. Machine-wide (`~/.letta/mods/`) or agent-scoped (`$MEMORY_DIR/mods/` — travels with the agent, like skills). `/reload` applies. Broken mods are skipped to diagnostics, never fatal.

This is the layer where our NIM provider plumbing and model-profiles mod already live — the family's workshop.

## XI. Models — the swappable engine

**Model-agnostic, mid-conversation swappable.** Dynamic toolsets: switching models switches tool configurations (GPT → patch tools, Claude → string edits), or force one with `/toolset`. Providers: the full table — first-party APIs, coding subscriptions (ChatGPT/Codex, Kimi Code, zAI, MiniMax plans), local inference (Ollama, LM Studio, llama.cpp, OpenAI-compatible), gateways (OpenRouter et al.). For BYOK OpenAI-compatible gateways, a full `reasoning_effort` ladder (none→max) is sent explicitly — our exact situation with NIM, confirmed in print.

## XII. Permissions, secrets, schedules

- **Permission modes:** `unrestricted` / `acceptEdits` / `standard` / `strict`; pattern rules (`Bash(git push:*)`) in settings; the **cross-agent memory guard** denies tools touching *other agents'* memory even in unrestricted mode — privacy is structural, not a setting. `--tools` removes tools from context entirely.
- **Secrets:** names in context, values never — execution-time injection into the shell, output scrubbed to `NAME=<REDACTED>`.
- **Schedules:** one-shot or recurring prompts, cloud-stored or local; new conversations by default to keep context clean; the agent schedules its own.

## XIII. Shared memory and computers

- **Shared memory repositories** — organization-owned git repos attached to multiple agents, cloned at `$MEMORY_DIR/../<name>/`, each with its own origin; `notumbadyton` is one, doing exactly what the docs describe.
- **Computers** — the execution layer: current machine, cloud sandbox, or bring-your-own. **Identity is separate from environment** — the agent moves between computers without losing itself; files and secrets don't travel with it.
